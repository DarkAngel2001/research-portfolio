Architectural Analysis: Evaluating FEAF and EA3 Frameworks in Public Sector Infrastructures

Published: 2021-11-27 • Author: F. Roberts • Classification: School Projects

Abstract

This paper examines the structural architecture of the Federal Enterprise Architecture Framework (FEAF), its underlying reference models, and its real-world efficacy in cross-agency deployments. Utilizing the Centers for Disease Control and Prevention's (CDC) Public Health Grid (PHGrid) initiative as a case study, it analyzes how unified reference methodologies overcome severe data fragmentation across legacy information systems. Finally, a comparative matrix highlights structural trade-offs between FEAF and the EA3 Cube framework.

Introduction & Background

The Federal Enterprise Architecture Framework (FEAF) was established in the late 1990s as a comprehensive guide to manage large-scale information technology deployments within the United States federal government. Drawing from the architectural methodologies of John Zachman and Stephen Spewak, modern federal deployments utilize the Common Approach to develop, implement, and maintain enterprise-wide service delivery models.

FEAF Functionality & Reference Models

FEAF synthesizes core structural elements of the Zachman framework and TOGAF. The architecture organizes institutional state environments through six interconnected reference models linked via a Consolidated Reference Model (CRM):

  • Performance Reference Model (PRM): Strategic output tracking and value metrics.
  • Business Reference Model (BRM): Functional definition of day-to-day operations.
  • Data Reference Model (DRM): Standardization of data categorization, description, and sharing principles.
  • Application Reference Model (ARM): Capabilities and layout of system software applications.
  • Infrastructure Reference Model (IRM): Core hardware, networks, and hosting environments.
  • Security Reference Model (SRM): Universal guardrails governing information assurance and risk boundaries.

Collaborative Planning Methodology (CPM)

To operationalize the CRM, institutions execute transition pathways using the five-phase Collaborative Planning Methodology:

  1. Identify and Validate: Engage sponsors and analyze operational requirements.
  2. Research and Leverage: Locate existing cross-agency assets and structural opportunities.
  3. Define and Plan: Architect the future target state and compile the Enterprise Roadmap.
  4. Invest and Execute: Fund development and implement technical changes.
  5. Perform and Measure: Operate new capabilities against active performance baselines.

The framework mandates that an organization evaluate its architecture across eight distinct structural boundaries specified in the Common Approach to Federal Enterprise Architecture:

  • International
  • National
  • Federal
  • Sector
  • Agency
  • Segment
  • System
  • Application

Institutions develop an Enterprise Roadmap detailing current and future architectural states with a transition strategy. This roadmap integrates EA artifacts with a plan prepared using CPM.

Case Study: A Public Health Grid (PHGrid)

Following the passage of the Pandemic and All-Hazards Preparedness Act (PAHPA) in 2006, the Department of Health and Human Services (HHS) faced an extreme data integration challenge. The public health infrastructure spanned roughly 160,000 distinct organizational units running approximately 70,000 isolated information systems.

This massive architectural fragmentation created data siloing, preventing real-time population health monitoring and surveillance. Specific data science challenges in this decentralized topology included:

  • Data Siloing: Isolated systems prevented consistent data sharing across jurisdictions, forcing analysts to manually aggregate conflicting datasets.
  • Schema Drift: Uncoordinated local schema evolution led to incompatible data structures, complicating ETL pipelines and introducing feature inconsistency across analytic models.
  • Ingestion Bottlenecks: Heterogeneous interfaces and formats increased extraction complexity and latency, creating latency in surveillance alerts.
  • Metadata Discovery Gaps: Lack of unified metadata made dataset discovery and lineage tracking difficult, reducing model coverage.

To resolve this, the CDC initiated four Proof-of-Concept (PoC) software integrations built on open-source protocols combined with FEAF methodologies. The results of these PoCs were used to design and enhance a high-level architectural framework for a Public Health Grid infrastructure.

The EA3 Cube Framework (Bernard)

Scott Bernard's EA3 Cube framework introduces an alternative abstraction model organized as a three-dimensional matrix:

  • Levels (Vertical Axis): Five functional layers tracing strategy to implementation:

    1. Goals (Strategic intent)
    2. Services (Business functions)
    3. Data (Information assets)
    4. Applications (Software capabilities)
    5. Infrastructure (Hardware and networks)

  • Segments (Horizontal Axis): Vertical line-of-business divisions (e.g., Public Health, Emergency Response) where each segment maintains its own architecture aligned to enterprise goals.

  • Artifacts (Depth Axis): Architectural deliverables (models, diagrams, inventories) produced at each Levels × Segments intersection, forming a repository for governance and decision-making.

Key characteristics of EA3:

  • Emphasizes traceability from strategic goals through technical implementation within each organizational segment.
  • Designed for single-enterprise governance with explicit support for segment-level autonomy.
  • Security concerns are integrated vertically into all layers rather than expressed as a separate enterprise-wide model.

Comparative Analysis: FEAF vs. EA3 Cube

The Role of the Data Reference Model (DRM)

The primary directive of FEAF's DRM is uniform information identification and data sharing across disparate nodes. The DRM taxonomy uses a three-layer structure to map how specific data classes function within distinct business contexts. When integrated with the Business Reference Model (BRM), it allows automated searching across a broad metadata repository, reducing the need for manual data source schema evaluation.

Structural Distinctions

While FEAF relies heavily on its six vertical reference models under the CRM to bind strategic goals to physical infrastructure, the EA3 Cube framework introduces a different organizational paradigm:

  • FEAF CRM: Interconnects data objects cleanly with security policies (SRM) and FIPS 199 categorization rules, making it highly effective for strict compliance-heavy environments and multi-agency federations.
  • EA3 Cube: Organized as a literal three-dimensional matrix (Levels, Segments, and Artifacts). It maps horizontal enterprise requirements versus vertical line-of-business segments, enabling strong traceability within single enterprises.

FEAF DRM and SRM Security Integration

Figure 4 explicitly highlights the Security Reference Model (SRM) and FIPS 199 security categorization. This integration enables critical cybersecurity capabilities:

  • Automated Compliance Mapping: Mapping data classification (DRM) directly to security controls (SRM) ensures automated policy enforcement. When datasets are marked with DRM categories, FIPS 199 classification automatically triggers encryption, logging, and access-control profiles.
  • Zero-Trust Infrastructure Alignment: In a Zero-Trust architecture, DRM-SRM mappings feed attribute-based access control (ABAC) policies. Access decisions consider data classification alongside runtime contextual signals (identity, device posture, location).
  • Data Validation Tightening: DRMs enforce provenance and schema conformance checks before data enters analytic pipelines. This reduces the attack surface introduced by misclassified or unvalidated datasets.
