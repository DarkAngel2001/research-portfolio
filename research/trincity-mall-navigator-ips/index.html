Trincity Mall Navigator: Engineering Indoor Positioning Systems via Native SDKs and No-Code Sensor Fusion

Published: 2022-07-26 • Author: F. Roberts • Classification: School Projects

Abstract

Outdoor navigation heavily relies on global navigation satellite systems (GNSS/GPS), which suffer severe attenuation when penetrating structural building materials. This project details the architectural design and implementation of the Trincity Mall Navigator, an Indoor Positioning System (IPS) engineered for micro-navigation across multi-level commercial structures. We evaluate the native deployment of the IndoorAtlas SDK within Android Studio alongside an agile comparative pivot utilizing rapid application development frameworks.

Company Background: Trincity Mall

Trincity Mall is the largest retail mall in the English-speaking Caribbean. It serves as the focal point for the HCL Group's Trincity Millennium Vision residential, commercial, and recreational developments. The mall receives over 100,000 visitors who frequent its mix of retail, dining, and recreational opportunities. Opened in 1984 with 80 retailers across 140,000 square feet, it has grown to over 500 stores filling 500,000+ square feet across multiple levels.

This scale creates significant navigation challenges: visitors frequently struggle to locate specific stores, relying on traditional wayfinding guides, staff inquiries, or trial-and-error navigation. An accurate indoor guidance system is crucial for such massive shopping facilities' profitability and customer experience.

Core Technology Stack & Architecture

Indoor positioning requires distinct algorithmic tracking models to overcome the lack of reliable GPS signals. The planned native architecture leverages three core technologies:

  • Android Studio & Java/Kotlin API: Handled the local application runtime environment, user interface rendering, and asynchronous event handling.
  • Google Maps API: Provided the geospatial layout, acting as the base canvas onto which custom local floor plans were programmatically overlaid.
  • IndoorAtlas SDK: A specialized cloud-connected tracking platform that utilizes sensor fusion—processing geomagnetic anomalies, Wi-Fi Received Signal Strength Indication (RSSI) fingerprinting, and smartphone inertial sensors (accelerometer/gyroscope via IMU) to map indoor coordinates.

Goal of Application

The Trincity Mall Tracker was designed to provide turn-by-turn indoor navigation for shopping mall visitors. Key objectives include:

  • Store-to-Store Navigation: Users select a destination store, and the app displays a marker pointing to their current position and the target store.
  • Floor Plan Selection: Users can choose building levels, with each floor's layout displayed on the Google Maps interface.
  • Search Functionality: Users search for shops by category or keywords, with results displayed in the same interface.
  • Store Information & Promotions: Selecting a store displays its details and current promotions.
  • Accessibility Support: Voice instructions and precise directions support visually impaired visitors who need trustworthy navigation tools.
  • Visitor Behavior Analytics: The system enables mall operators to study visitor movements and assess sales/marketing performance for immediate strategic adjustments.

Requirement Specification

User Functions:

  1. Create account and log in
  2. View shop list with categories
  3. Search for shops by keyword/category
  4. View map of shopping mall with floor selection
  5. Get direction guide to navigate to desired store
  6. View store information and latest promotions

Access Control: After successful registration and login, users access three primary functions via the menu:

  • Lists of businesses, shops, and kiosks
  • Map interface with floor-level selection
  • Search Shop function

Map Interface: Displays the shopping mall layout. Users select locations by floor level, with each level's map displayed. Search results appear in the same interface, allowing users to view store information or launch the navigation guide.

Implementation Methodology

Phase 1: Floor Plan Geospatial Calibration

Before integrating tracking scripts, physical blueprint graphics of Trincity Mall were aligned with real-world geographic coordinates. Using floor plan placement tools, anchors were set at explicit latitude and longitude coordinates, ensuring that the structural scale factor accurately corresponded to the underlying Google Maps grid.

The IndoorAtlas Dashboard web portal manages floor plans, maps, API keys, and applications. Floorplans define indoor coordinate frames bound to the standard global coordinate system. All floorplans must be assigned a floor number determining correct vertical ordering within the location.

Phase 2: Sensor Fingerprinting and Waypoint Mapping

To build the positioning database, a physical survey of the environment was conducted using the IndoorAtlas MapCreator 2 mobile interface:

  1. Signal Fingerprinting: Captured local variations in the ambient geomagnetic field and recorded signal strengths of stable, static Wi-Fi access points.
  2. Path Generation: Mapped interconnected waypoints to form a routing graph, defining accessible walking channels for users.

Before mapping, routes were planned to collect data systematically. Waypoints function as confirmation points for data collection paths. After mapping areas marked by waypoints, routes were reviewed in the Dashboard. Once verified, maps were generated with Wi-Fi coverage quality metrics.

Engineering Pivot: Native Development vs. Rapid Prototyping

Due to sudden project deployment constraints and limited development windows, the project architecture underwent an agile adjustment. The secondary iteration moved from native IDE compilation to SAP AppGyver (a visual no-code development ecosystem), offering a valuable comparative study between full-stack native engineering and rapid application prototyping.

Planned Project: Native Android / IndoorAtlas SDK

Development Tools:

  • Android Studio: Official IDE for Google's Android operating system, available on Windows, macOS, and Linux. Features include Gradle-based build support, Android-specific refactoring, and ProGuard integration. Replaced Eclipse Android Development Tools (ADT) as the primary IDE for native Android applications.

  • IndoorAtlas SDK Features: Location updates, floor detection, cloud storage. Uses three hardware sensors (magnetometer, accelerometer, gyroscope) and Wi-Fi when available. Functions with limited capability if some sensors are unavailable.

  • Google Maps Features: Internal navigation for selected buildings in the US and UK parts. Allows map downloads, travel assistance, turn-by-turn outdoor navigation, and route planning. Offers satellite, panoramic, and street view modes for better UI.

Implementation Steps:

  1. Displaying Maps on Screen: The onMapReady() function displays maps. The activity layout file requires a <fragment> element with SupportMapFragment as the Google Maps container.

  2. Adding Floor Plan Overlay: Ground overlays are image overlays tied to latitude/longitude coordinates, moving when the map is dragged or zoomed. The floor plan bitmap serves as a ground overlay, letting users check location on the floor plan.

  3. Adding IndoorAtlas SDK Dependency: For new Gradle projects, IndoorAtlas recommends AAR format (contains Java classes and AndroidManifest.xml template merged during build). The SDK requires three hardware sensors and Wi-Fi. Declaring these in the manifest restricts Google Play device compatibility but ensures full performance.

    During runtime, the SDK checks for permission grants and Bluetooth service enablement. Beacon support is silently ignored if conditions aren't met. By default, the SDK does not add required permissions to scan beacons. Every application needs unique API Key and Secret strings managed via IndoorAtlas Applications.

  4. Retrieving User Location: For Android 6+ phones, Runtime Permissions must be added for Location Updates. This specially requests users to enable Location, Bluetooth, and Wi-Fi. Required permissions include:

    • Manifest.permission.CHANGE_WIFI_STATE
    • Manifest.permission.ACCESS_WIFI_STATE
    • Manifest.permission.ACCESS_COARSE_LOCATION
    • Manifest.permission.ACCESS_FINE_LOCATION

    The ensurePermissions() function checks if ACCESS_FINE_LOCATION is granted, shows rationale dialogs if needed, and requests permissions via ActivityCompat.requestPermissions(). The onRequestPermissionsResult() handler processes grant results.

  5. IndoorAtlas Mapping: After aligning floorplans and adding waypoints, routes are reviewed in the Dashboard. Once verified, maps are generated with Wi-Fi mapping coverage quality metrics.

Final Project: SAP AppGyver Environment

The final version utilized AppGyver's no-code functionalities with changes to provided functions for this application's use.

AppGyver Features:

  • API integration using REST integration wizard
  • Native performance claims
  • Unlimited logic (supposedly)
  • Visual orchestration without complex coding environments
  • Internal application creation for mobile forms, data collection, and workflow automation

Final Implementation: The Home page lists five stores, with one functional for demo purposes (Marios, with the only displayable route to Sports and Games). The functionality testing whether the user is at Trincity Mall is operational. If the user is not at the mall, a preset map with markers for the user is displayed.

Security, Privacy, and Data Engineering Considerations

1. Sensor Fusion Optimization (Data Science Perspective)

From a data science perspective, indoor positioning accuracy hinges on state-estimation algorithms. Because individual Wi-Fi RSSI signatures fluctuate constantly due to human body attenuation and structural changes, the application relies on the magnetometer to detect subtle anomalies in structural steel beams, smoothing out tracking inconsistencies via real-time filtering.

Technical Sensor Fusion Mechanism: IndoorAtlas employs Hybrid Indoor Positioning Technology, combining:

  • Geomagnetic Field Data: Magnetometer telemetry detects structural steel anomalies unique to each building's architecture
  • Wi-Fi Fingerprinting: RSSI values from stable access points provide coarse locationSeason
  • Inertial Measurement Unit (IMU): Accelerometer and gyroscope data enable step detection and direction tracking

These sensor streams are processed via Kalman filtering or probabilistic state-estimation algorithms to produce sub-meter tracking accuracy in closed spaces.

2. Protecting Location Privacy (Cybersecurity Perspective)

Continuous interior location tracking captures sensitive user metrics, including dwell-time parameters and individual shopping trajectories. To secure this surface, any production-ready deployment must enforce strict security guidelines:

  • Identifier Anonymization: Device MAC addresses and hardware profiles must be securely hashed on-device using cryptographic algorithms (such as SHA-256 with a unique salt) before uploading metadata to positioning servers. This prevents unauthorized third-party tracking or behavioral profiling.

  • Transport Encryption: All telemetry data transmission between the mobile client application and the IndoorAtlas cloud backend must travel exclusively over TLS-encrypted channels (TLS 1.3 minimum) to prevent local sniffing or man-in-the-middle injection attacks.

  • Client-Side Processing: Location data should be processed client-side where possible, minimizing server-side exposure of raw biometric telemetry.

  • Data Minimization Policies: Collect only essential location data required for navigation functionality, discarding historical trajectory data after session completion unless explicitly consented for analytics.

  • Runtime Permission Best Practices: Request only necessary permissions (Location, Bluetooth, Wi-Fi) with clear user rationales explaining why each is required for indoor navigation functionality.

Development Environments

Three Primary App Environments:

  1. Development Environment: Where technical programming takes place. Developers construct apps ranging from platform-specific native apps to progressive web apps and cross-platform apps.

  2. Staging (Testing) Environment: After technical development completes, the web app is sent here for debugging and realistic environment testing. Since this mobile application is strongly reliant on a physical environment, it was thoroughly tested at Trincity Mall for accuracy and geographical location matching.

  3. Production Environment: The environment used during development and for the app's launch. Available to the public with updated information. The finished version ready for commercial purpose begins here.

Platform Considerations: Development platforms vary by capability. Low-code platforms allow users to view architecture and design without modifying code while providing monitoring analytics and developer assistance. Visual Studio with Microsoft Xamarin represents viable cross-platform development solutions supporting both iOS and Android.

Conclusion

Building an Indoor Positioning System highlights the challenges of sub-meter tracking in closed spaces. GPS technology works accurately outdoors but fails inside structures due to signal attenuation through building materials.

Using the IndoorAtlas SDK, I successfully mapped inside a building and obtained position data using Wi-Fi, Bluetooth, and geomagnetic sensors. While location accuracy showed some inconsistency, perfect mapping would achieve more precise results.

This project demonstrated both the technical requirements of sensor-driven navigation and the practical agility needed to pivot when development resources change. The comparative analysis between native SDK development (Android Studio + IndoorAtlas) and no-code prototyping (SAP AppGyver) revealed critical trade-offs:

  • Native Development: Offers complete hardware API access, custom background processing, and granular sensor control but requires slower development velocity and specialized expertise.

  • No-Code Prototyping: Enables exceptional development velocity through visual logic blocks but constrains granular control and limits deep hardware access.

By combining architectural mapping with adaptive prototyping tools, this project validated the feasibility of IPS implementation for multi-level commercial structures while highlighting the importance of selecting development methodologies aligned with project constraints and technical requirements.
