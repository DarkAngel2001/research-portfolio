Research Prospectus: A Secure Framework for Integrating Large Language Models in Public Sector Information Systems

Published: 2026-05-27 • Author: F. Roberts • Classification: Professional

Abstract

This research framework outlines an end-to-end technical and managerial governance model enabling public sector institutions to leverage generative AI safely. By developing a containerized, privacy-preserving data pipeline layer for Retrieval-Augmented Generation (RAG), this study empirically quantifies the utility-privacy trade-offs associated with Named Entity Recognition (NER) masking, tokenization, and differential privacy constraints on embedding vectors. The final framework cross-maps technical mitigation strategies against international readiness indicators, establishing a secure blueprint for public sector technical deployments.

1. Background & Motivation

1.1 Trinidad and Tobago's AI Policy Environment

Trinidad and Tobago is actively building a structured, evidence-based national AI strategy. Led by the Ministry of Public Administration and Artificial Intelligence (MPAAI) in partnership with UNESCO and the UNDP, the country launched its national AI readiness baseline using the UNESCO Readiness Assessment Methodology (RAM) in early 2026. The UNESCO RAM national validation workshop was held on Friday 27 February 2026 at The University of the West Indies, St. Augustine.

This approach covers five critical socio-technical areas:

  • Legal & Regulatory.
  • Technological & Infrastructural.
  • Societal & Cultural.
  • Scientific & Educational.
  • Economic.

This exploration is further supported by policy demands from the ground up, including the 2024 National Youth Parliament motion calling for age-appropriate AI regulations and robust data privacy guardrails within digital educational frameworks.

1.2 Japan's National AI Strategy

Concurrently, Japan’s Basic Plan on AI Development and Use was adopted by the Cabinet on December 23, 2025. The plan seeks to accelerate the adoption of generative AI systems across local and central government offices while strengthening safeguards, and it is tied to Japan’s broader AI policy direction and Society 5.0 vision.

The policy direction is organized around four basic pillars:

  • Accelerating AI adoption.
  • Strategically strengthening AI development capabilities.
  • Leading AI governance.
  • Continuous transformation toward an AI-enabled society.

Backed by the AI Promotion Law of May 2025 and audited via the Japan AI Safety Institute, Japan’s strategy prioritizes structural trust, technical reliability, and secure deployment models within its Society 5.0 vision.

1.3 Critical Security Surfaces & Structural Vulnerabilities

Direct integration of unflagged commercial cloud LLMs introduces major security vulnerabilities to public workflows. These include:

  • Data Leakage: inadvertent ingestion of sensitive citizen data or policy drafts into external model training arrays.
  • Prompt Injection (OWASP LLM01): malicious manipulation of user instructions to bypass system guardrails and access restricted administrative files.
  • Vector Database Vulnerabilities (OWASP LLM08): unauthorized retrieval of high-value metadata records or unredacted information chunks through poorly isolated semantic search spaces.

The 2025 OWASP LLM updates explicitly identify LLM01 Prompt Injection and LLM08 Vector and Embedding Weaknesses as major risks in retrieval-augmented generation and vector database deployments.

2. Research Objectives & Specific Aims

The core goal of this master’s research is to develop a modular, verifiable technical pipeline that allows government agencies to securely implement RAG frameworks without risking data confidentiality or violating statutory policy bounds.

2.1 Ultimate Goal

Develop an end-to-end, interdisciplinary technical and managerial framework (governance model) enabling public sector institutions in both Trinidad and Tobago and Japan to fully leverage LLM capabilities while ensuring:

  • Absolute data confidentiality (no PII/financial/student data leakage).
  • Full auditability (immutable logs for external regulatory review).
  • Statutory regulatory compliance (alignment with UNESCO RAM dimensions, NIST Privacy Framework, Japan AI Guidelines, emerging T&T AI policy).

2.2 Specific Research Aims

Aim 1: Design Privacy-Preserving Anonymization Algorithms
Develop an automated data pre-processing pipeline featuring:

  • Named Entity Recognition (NER) using domain-adapted transformer models.
  • Differential privacy constraints with tunable epsilon parameters balancing utility-privacy trade-off.
  • Tokenization/hashing mechanisms for sensitive attributes before data reaches the LLM environment.
  • Data discovery and classification hooks identifying sensitive data before ingestion.

Aim 2: Formulate System Architecture Defenses Against LLM-Specific Vulnerabilities
Engineer defenses targeting OWASP Top 10 for LLM (2025):

  • Prompt Injection Mitigation: input/output filtering, semantic analysis, RAG Triad assessment.
  • Vector Database Security: permission-aware vector stores with fine-grained access controls.
  • Containerized Network Isolation: Docker/Kubernetes environments preventing external model-training loop data retention.
  • API Security: ephemeral scoped credentials, privilege control with least-privilege access.

Aim 3: Establish Automated Governance Evaluation Protocol
Create a compliance verification system featuring:

  • LLM-as-a-Judge architecture: secondary restricted security model monitoring primary model outputs for data compliance.
  • SR 11-7 Model Risk Management governance: treating the LLM judge as a model requiring validation, ongoing monitoring, human-in-the-loop design, and bias testing.
  • Immutable audit logging: detailed logs of retrieval activities for compliance reporting.
  • Continuous monitoring: ML-based behavioral baseline and anomaly detection with automated alerts.

3. Technical Pipeline and Privacy Layer

3.1 Technical Pipeline Overview

The technical process can be represented as a layered pipeline:

Raw Input Data │ ▼ Data Classification Hooks │ └─ Evaluates asset sensitivity scores ▼ Transformer-Based NER │ └─ Detects names, IDs, addresses, financial data, and other sensitive entities ▼ Masking & Tokenization of PII │ └─ Replaces sensitive fields with protected placeholders or hashes ▼ Noise Perturbation Layer │ └─ Calibrates DP noise (ε ≤ 1.0) on selected representations ▼ Permission-Aware VDB │ └─ Applies cleartext Boolean access control arrays for retrieval filtering ▼ Local Containerized LLM │ └─ Performs local context inference loop without exposing raw sensitive data

3.2 The Privacy-Preserving Data Pipeline Layer

This is the core privacy layer the research proposes. Its purpose is to mediate public-sector data before it reaches the RAG environment, ensuring that raw sensitive content is not directly exposed to the model or the vector store.

The privacy-preserving layer performs the following functions:

  • Data discovery and classification: identifies whether incoming records contain sensitive assets.
  • NER-based masking/replacement: detects personally identifiable information and replaces it with protected forms.
  • Tokenization/hashing: transforms sensitive attributes so they can be referenced without revealing cleartext identity.
  • Differential privacy perturbation: applies controlled noise to embeddings and related representations to reduce re-identification risk.
  • Permission-aware metadata handling: stores access-control information in cleartext for ACL filtering, not hashed, so retrieval permissions can be enforced properly.
  • Local containment: keeps the raw sensitive data and the LLM inference workflow inside a trusted environment.

This privacy layer is important because the proposal is not simply about classification or masking in isolation. It is about constructing a full data protection stage between raw public-sector records and the downstream RAG system so that utility can be preserved while leakage risk is reduced.

3.3 Why the Privacy Layer Matters

The proposal explicitly evaluates the utility-privacy trade-off when applying:

  • PII detection.
  • NER-based masking/replacement.
  • Tokenization/hashing.
  • Differential privacy on embeddings.

The privacy layer is designed to support both countries’ public-sector use cases, including student records, procurement data, health records, citizen PII, financial instruments, and national security documents, while preserving enough signal for retrieval and generation tasks.

3.4 Specific Aims in Pipeline Form

  1. Implement a reproducible pipeline for data discovery/classification, NER-based PII protection, tokenization/hashing, and configurable differential privacy on embeddings.
  2. Quantitatively evaluate DP effects on RAG utility across epsilon values by measuring retrieval accuracy, relevance, and generation fidelity.
  3. Demonstrate end-to-end feasibility with a local, containerized LLM plus permission-aware vector DB using synthetic or redacted public-sector datasets.

Deliverables:

Phase 1.2: Public Dataset Characterization & Risk Assessment Matrix Development

Months 4–6

Activities:

  • Dataset categorization for Trinidad & Tobago:
    • Education sector: student records, academic performance data, classroom AI interactions.
    • Procurement records: contract values, vendor information, bidding details.
    • Municipal minutes: council discussions, policy decisions, citizen complaints.
    • Health sector: patient records, health statistics.
  • Dataset categorization for Japan:
    • Citizen PII datasets: national ID, health records, tax information.
    • Government procurement: contract values, vendor information.
    • Policy documentation: regulations, guidelines, procedural manuals.
    • National security documents: classified information, law enforcement records.
  • Sensitivity Classification:
    • Tier 1 (Low): publicly available information, no PII.
    • Tier 2 (Medium): internal operational data, limited PII.
    • Tier 3 (High): sensitive PII, financial instruments, legally restricted data.
  • Risk Assessment Matrix Development:
    • Data leakage to external model training.
    • Prompt injection compromising system integrity.
    • Compliance violation triggering regulatory penalties.
    • Quantitative risk scoring where Probability ∈ {1–5}, Impact ∈ {1–5}.
  • Stakeholder Interviews:
    • 3–4 Trinidad & Tobago public sector IT managers.
    • 3–4 Japanese public sector IT managers.

Deliverables:

  • Dataset classification framework with sensitivity tiers.
  • Risk assessment matrix with quantitative scoring model.
  • Comparative stakeholder needs analysis report.
Phase 1.3: Privacy-Preserving Data Preprocessing Pipeline Design

Months 7–9

Activities:

  • NER Model Development:
    • Python-based workflow using spaCy and Hugging Face transformers.
    • Target entities for Trinidad & Tobago: student PII, procurement financial data, health records.
    • Target entities for Japan: citizen PII, financial instruments, national security data.
    • Training data: annotated corpus of public sector documents from both countries.
  • Differential Privacy Implementation:
    • Library: Google’s Differential Privacy library or OpenMined’s PySyft.
    • Mechanism: add calibrated noise ensuring differential privacy.
    • Utility-privacy trade-off: tune parameter, with target for high-sensitivity data like student records.
  • Tokenization/Hashing Mechanisms:
    • Sensitive attribute masking: replace PII with deterministic hashes or synthetic tokens.
    • Reversibility control: key management system ensuring only authorized processes can reverse tokens.
    • Consistency with Thales CipherTrust approach: classification, tokenization, encryption, masking through prebuilt hooks.

Deliverables:

  • Data preprocessing pipeline prototype (Python codebase, ~2,000 lines).
  • NER model trained on public sector documents from both countries.
  • Technical documentation for privacy-preserving preprocessing module.

Phase 2: Secure System Architecture Design, Vulnerability Testing, and Framework Synthesis

Months 13–24

Phase 2.1: Secure Containerized Environment Architecture Design

Months 13–15

Activities:

  • Containerized Environment Engineering:
    • Platform: Docker containers orchestrated via Kubernetes.
    • Local open-source LLMs: Llama 2/3, Mistral 7B, or Falcon 40B.
    • Isolation: network isolation preventing external data exfiltration.
    • Infrastructure-as-Code: Terraform/Ansible scripts for reproducible deployment.
  • Secure API Gateway Configuration:
    • Framework: FastAPI with programmatically enforced security constraints.
    • Prompt retention prevention: ensure user prompts are not retained for external model-training loops.
    • Model Context Protocol (MCP): implement MCP for safely connecting models with tools.
    • Credential management: ephemeral scoped credentials replacing static API keys.
  • Permission-Aware Vector Database Architecture:
    • Database: Qdrant or Milvus with fine-grained access controls.
    • Access partitioning: strict logical partitioning prevents unauthorized access between user groups.
    • Encryption: CipherTrust Transparent Encryption (CTE) for vector database storage at rest.

Deliverables:

    • Output: score plus reasoning explanation with high agreement relative to human evaluators.
  • SR 11-7 Model Risk Management Governance:
